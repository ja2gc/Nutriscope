# Notifications, FSS Reports, and Mobile UX Redesign

Date: 2026-07-19

## Objective

Make notifications reliable and actionable on the website and mobile app, give Food Service Staff access to only their own generated accomplishment reports, separate meal preparation from accomplishment logging, and modernize the mobile application without changing Nutriscope's established brand colors.

The mobile visual direction combines the clear task hierarchy and compact day navigation of [Taskpilot](https://www.behance.net/gallery/245333715/Taskpilot-Task-Management-Mobile-App-Figma-UI-Kit) with the approachable dashboard hierarchy of [Loag](https://www.behance.net/gallery/126865193/LOAG-HR-Payroll-Task-Management-Mobile-App-UI). These are inspiration references only. Nutriscope will use original components, layouts, and assets.

## Product Decisions

### Notification destinations

Every notification exposes a public source UUID and a deterministic destination:

- Announcement: the announcement board with the target announcement opened.
- Purchase order awaiting receipt: the procurement page with the target PO detail and receipt/data-entry controls opened.
- NCP follow-up: the owning RND's patient/NCP workflow at the follow-up monitoring action.

Website and mobile clients use the same source-module/type mapping. Raw database IDs are never used in public routes.

### Notification lifecycle

Reading and acting are separate states:

- `read_at`: the user has seen or marked the notification as read.
- `opened_at`: the user clicked the notification and the client began navigating to its target.
- `resolved_at`: the task represented by an action notification is complete.

The existing `read` boolean remains for backward compatibility and fast unread counts. Mark-all-read sets `read` and `read_at`, but not `opened_at`; this prevents bulk-marking from prematurely starting retention.

Retention is three days after the qualifying event:

- Announcements are pruned only when `opened_at` is at least three days old.
- PO notifications are resolved after all required vendor groups have a receipt attachment, then pruned three days after `resolved_at`.
- Follow-up notifications are resolved after a new monitoring entry is created for that NCP after the notification was issued, then pruned three days after `resolved_at`.
- Unread, unopened, or unresolved action notifications are retained.

A daily scheduled command performs pruning. Resolution is recorded at the domain action and the pruning query remains idempotent.

### FSS website reports

The shared reports page becomes role-aware:

- RND retains the full RND catalog and `/api/rnd` endpoints.
- FSS sees only the accomplishment-report catalog and calls `/api/fss` endpoints.
- Backend ownership scoping remains authoritative: FSS can list, view, and download only reports generated by their own user account.
- Admin behavior remains unchanged.

FSS also receives the website notification bell because notification APIs are already shared across authenticated roles.

### Mobile information architecture

The bottom navigation has five focused destinations:

1. Home
2. Menu
3. Meal Prep
4. Accomplishments
5. Procurement

The current combined Prep & Accomplishment screen is split. Accomplish contains Daily Log and My Reports. Announcement is the second of six bottom tabs; report details stay within Accomplish.

### Mobile menu day picker

The Menu Plan screen uses a Taskpilot-inspired horizontal day picker at the top:

- Compact weekday and date cells.
- Strong selected-day state using Nutriscope green.
- Immediate menu-content update on selection.
- Automatic scrolling to the active day when needed.
- Planned population and total served remain visible in a compact summary beside/below the picker.
- The user does not scroll through every menu day to reach the desired day.

The selected date is presentation state only; existing menu-cycle, population, and served-population APIs remain authoritative.

### Menu food and recipe profiles

Tapping a food or recipe on a selected menu day opens its existing food/recipe profile. When an RND assigns the estimated served population and converts the shopping list into a purchase order, the backend-generated PO snapshot is the authoritative scaling source. Mobile and website profiles show the same frozen per-item and ingredient quantities from that snapshot. Clients do not recalculate or silently substitute the current recipe after conversion.

## Visual System

The app keeps Nutriscope's green brand and warm neutral surfaces. The redesign uses:

- High-contrast white and soft-neutral surfaces rather than decorative gradients.
- Rounded but restrained cards, 12-16 px radii, and subtle borders/shadows.
- Clear type hierarchy with concise labels and numeric emphasis.
- Status chips for pending, completed, ordered, received, and attention states.
- Minimum 44 px touch targets and visible pressed/loading/disabled states.
- Consistent page padding, section spacing, empty states, errors, and skeleton/loading feedback.
- Original Lucide iconography already available in the app.

Taskpilot contributes the compact calendar/day selector, progress/status organization, and task-first information density. Loag contributes approachable dashboard cards, service shortcuts, and clear section hierarchy. Nutriscope avoids copying their proprietary art, files, or exact layouts.

## API and Data Contract

Notification and report public IDs are UUID strings on both clients. TypeScript interfaces and function parameters must match this contract.

The notification API adds an authenticated owner-scoped open action. It marks the notification read and records `opened_at` atomically. Existing read and read-all routes remain available.

All new mutations enforce notification ownership. Destination mapping remains client-side because routes differ between Next.js and Expo Router, while source UUID resolution remains server-side.

## Error Handling

- A notification without a valid destination is still readable but shows a non-destructive message instead of navigating incorrectly.
- A deleted source produces a safe unavailable state; it must not expose an internal ID.
- Deep-link navigation marks `opened_at` only after the open request succeeds. If the network fails, the client may still navigate but must surface retryable notification state rather than delete anything.
- Report authorization remains server-enforced even if a client route is manually modified.

## Testing and Blast Radius

Backend feature tests cover ownership, timestamps, opening, resolution, pruning, idempotency, and source UUIDs. Existing notification trigger, pagination, PO lifecycle, monitoring, and report-scope suites are regression coverage.

Menu-cycle regression tests also cover estimated-population scaling, frozen PO snapshots, profile visibility, and parity between the RND website response and mobile response consumption.

Frontend tests cover notification destination mapping, FSS report routing/catalog, and FSS bell visibility. Mobile static/unit contract tests cover UUID IDs, destination mapping, the five-tab split, and the day-picker/menu population integration. TypeScript checks validate the complete mobile and website contracts.

Final QA includes sequential Laravel tests, Pint, frontend lint/tests/build, mobile TypeScript validation, Expo diagnostics, route review, and an Android APK build. Existing unrelated user changes are excluded from the implementation commit.
