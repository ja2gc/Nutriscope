## Exact unit and nutrient contract

Luna must implement these values as written, not choose conversion factors during coding. `factor(from,to) = baseFactor[from] / baseFactor[to]` only within one family.

| Family | Canonical picker values and base factors | Allowed choice |
| --- | --- | --- |
| Mass, base g | `mg=0.001`, `g=1`, `kg=1000`, `oz=28.349523125`, `lb=453.59237` | Any listed mass unit when Ingredient baseline is mass. |
| Volume, base mL | `mL=1`, `L=1000`, `tsp=4.92892`, `tbsp=14.7868`, `cup=236.588` | Any listed volume unit when Ingredient baseline is volume. |
| Count | `piece` | `piece` only for a `piece` baseline. Existing nonempty legacy count-like units match only themselves. |

Normalize case/space and existing word aliases (`gram(s)`, `milliliter`, `millilitre`, `cc`, `liter`, `litre`, `teaspoon`, `tablespoon`; `pc`/`pcs`/`pieces` → `piece`). Do not show alias duplicates in the picker. Do not offer count↔mass, count↔volume, mass↔volume, unknown new units, or Food Service's Non-Auto Grocery free-text option. Missing/zero baseline is invalid. Example: `0.5 kg` against `100 g` → `0.5×1000/100 = 5` nutrient baselines; `1 cup` against `100 mL` → `236.588/100 = 2.36588` baselines.

USDA may describe a portion as `1 piece`, but its gram weight belongs to that specific food. Keep `piece` as an exact clinical count baseline only when nutrients for that measured piece are known; do not infer a universal piece weight. USDA Foundation/FNDDS/SR nutrients are generally per 100 g; branded records may be per 100 g or 100 mL. The current importer hardcodes `100 g`, so inspect the actual USDA nutrient basis and correct handling of volume-based branded records without adding another unit family or applying density assumptions.

For nutrient `k`: `row_k = ingredient_k × converted_recipe_quantity / ingredient_serving_size`; `batch_k = sum(row_k)`; `per_serving_k = batch_k / recipe_yield`; `planned_k = per_serving_k × consumed_servings`. This applies to calories, macros, water, and each micronutrient; keep intermediate values unrounded. For an Ingredient baseline change within a family, `new_serving_size = old_serving_size × factor(old_unit,new_unit)`; leave recorded recipe row amounts and per-baseline nutrient values unchanged. New Menu Plan/template recipe lines store `quantity` in `serving` units. For a legacy template line with a verified prepared-portion measure, `consumed_servings = converted_old_quantity / prepared_portion_amount`; otherwise require correction before new use. A five-serving batch with 500 g of an Ingredient and 1.2 planned servings produces `500×1.2/5 = 120 g` in the report patient column.

Persist Ingredient serving sizes and recipe row quantities to six decimal places through forward migrations. Store planned servings to two decimals, step/minimum `0.01`; save recipe macro/water totals to two decimals and micronutrients to three after summation. The PDF shows at most one decimal for ingredient amounts and servings, trims trailing zeroes, and shows positive values below 0.1 as `<0.1` rather than zero. Server values are authoritative; the frontend preview must agree.
