## Inventory and Food

- [x] Inventory presents one current unit, cost per unit, and default vendor. Preserve the existing item identity and unrelated fields.
- [x] Food recipes retain their own ingredient quantities, units, and baseline serving counts. Compatible mass and volume conversions produce correct cost and scaled amounts; incompatible units never produce guessed cost or Shopping List quantities.
- [x] Every Food and editable Menu Calendar ingredient requires a baseline quantity and measured unit. Non-Auto Grocery ingredients scale in their recipe unit even when it differs from Inventory; they contribute no automatic recipe cost or Suggested Shopping List quantity. Manual Shopping List addition uses the Inventory unit.
- [x] Add an independent per-ingredient **Adjust to taste** checkbox. Profile views group checked ingredients below a short note while still scaling their quantities. Non-Auto status alone must not put ingredients (such as rice) in that group. Preserve the marker in editable slots and frozen PO profiles; remove the former unmeasured `to taste` unit behavior.
- [x] Keep the FSS/mobile Food profile view only. The **Adjust to taste** note is cooking guidance, with no quantity edit there; RND Food and editable Menu Calendar editors remain available.
- [x] Auto Grocery ingredients use a positive measured quantity and a unit compatible with the Inventory unit. Existing incompatible Auto Grocery ingredients remain visible and excluded until corrected.
- [x] Switching an Inventory item to Auto Grocery checks all linked recipes. When all convert, save directly. Otherwise show the affected recipes with quantity/unit editing controls and save the Inventory flag plus recipe corrections only after all are valid. Leaving the correction flow leaves all records unchanged.
- [x] Include incompatible editable Menu Calendar slot overrides in that correction popup and atomic save. Keep completed PO snapshots frozen. Capture a screenshot of the popup during a deployed live-browser sweep for the user.
- [x] Replace inline correction fields with a cached clickable list of affected Foods and editable Menu Calendar slots. Open each item's page for only the affected quantity and unit, return Back to the same list, stage corrections without changing saved records, and commit all corrections with the Inventory update only after every item is complete. Limit each correction's unit choices to the category of the proposed Inventory unit. The user confirmed this page scope and atomic save.
- [x] Changing an Inventory unit to a compatible unit leaves recipe entries intact, automatically converts Cost/unit to preserve the underlying price, and converts calculations. An incompatible change uses the same affected-recipe correction flow; no silent relabeling or guessed quantity.
- [x] Inventory filter distinguishes Auto Grocery and Non-Auto Grocery. Auto Grocery unit choices exclude sack and other unconvertible package units; do not invent package conversion ratios.

## Menu Calendar and Shopping Lists

- [x] Generate a Suggested Shopping List across arbitrary ranges and Menu Cycle boundaries. One Estimated servings input sets each applicable Menu Calendar day’s `estimate_population` only when Save succeeds; preview does not mutate either record. Saved lists then use the current per-day estimates, never `served_population`, and scale each Food from its own baseline servings.
- [x] Aggregate compatible Auto Grocery requirements across dates. Keep Non-Auto Grocery out of automatic items; preserve manual additions.
- [x] New Suggested lists remain unsaved drafts during review. **Save Shopping List** persists the list without creating a PO; reopening edits the same record.
- [x] First-save confirmation appears from direct Save and Back > Save. Approved copy explains day estimates, editable working status, and separate Turn Into PO. Direct Save offers **Save Shopping List** / **Keep Editing**; Back with unsaved work offers **Save** / **Discard**.
- [x] Edits to saved lists remain unsaved until Save. Back > Discard drops only those edits; for a new list it drops the draft. Saved active lists permit Unit, Cost/unit, Vendor, and other existing procurement edits.
- [x] Active saved Suggested lists recalculate their generated requirements when covered Menu Calendar `estimate_population` changes. Preserve deliberate manual additions and procurement edits. Stop recalculation at Turn Into PO, when the Shopping List becomes read-only under the user’s later decision.
- [x] The single Estimated servings value remains editable on a saved Suggested list until Turn Into PO. Save applies it to every covered Menu Calendar day and recalculates generated quantities; Back > Discard leaves the saved count unchanged. PO conversion locks the input. This is the user's 2026-10-12 clarification.
- [x] Shopping List unit choices and server validation allow only units compatible with the Inventory unit and linked Auto Grocery recipes. Changing unit converts the displayed requirement and cost per unit, preserving total value until a user changes the procurement estimate.
- [x] Per-item Shopping List quantity can be left as calculated, rounded to the nearest whole unit (.5 up), or manually changed. These choices affect the purchase line only, never Estimated servings or Food scaling. Rounding reapplies to recalculated requirements.
- [x] Block Suggested list generation/save when any applicable service day already belongs to an existing saved Suggested list. Identify conflicting dates. Deleting the existing list releases coverage. Manual and Supplies lists neither consume nor block this coverage.
- [x] Suggested lists retain selected start/end dates and display the start as primary business date. Manual and Supplies lists require a user-selected procurement date; creation time is not substituted.

## Purchase Orders and completion

- [x] **Turn Into PO** is a separate explicit action available for a saved list. It creates one PO with multiple vendor groups, including a functional Unspecified group, and locks the source Shopping List.
- [ ] Before **Turn Into PO** converts a saved list, show a short warning that the Shopping List will become read-only. **Cancel** keeps the list editable; **Turn Into PO and lock list** confirms conversion. Verify the warning and Cancel on the deployed page.
- [x] PO captures Shopping List values at conversion. Its Unit is locked; later Inventory, Food, Menu Calendar, and Shopping List changes cannot silently alter it. Lock covered Menu Cycle content as required by the existing lifecycle.
- [x] PO keeps planned quantity separate from actual purchased quantity. Actual Quantity, Actual Unit Price, and Actual Total are editable with the specified two-way calculation. Whole-number steppers; no redundant calculation fields.
- [x] Each vendor group shows Receipt Total as the sum of its item Actual Totals. Served Days and Total Served Population belong to the PO as a whole, using actual `served_population` and counting each service date once. Vendor groups do not need a day-to-item assignment or vendor-level population totals.
- [x] On confirmed PO completion, update only the corresponding Inventory Unit, Cost/unit, and Vendor from final PO values. Inventory default Vendor always follows the latest completed PO; remove the existing Inventory vendor lock and its blocking behavior. Actual Quantity and Actual Total remain PO history. Preserve receipt/proof/authorization rules and do not update Inventory prematurely.
- [x] FSS may edit PO actual item quantities/prices and upload receipt/proof, but cannot mark a Vendor group received. RND marks it received on web Procurement after reviewing values and evidence. Enforce this in the shared API and remove the FSS/mobile completion control.
- [x] Verify the existing budget ledger records one completed-PO deduction with the correct amount and fiscal year. Fix it only if focused integration evidence shows a defect.
