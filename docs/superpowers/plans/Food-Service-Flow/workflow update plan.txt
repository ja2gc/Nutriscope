--- STEP 1: Estimated Population + Recipe Scaling ---

The system has two completely separate population fields that must never be
confused or overwrite each other:

estimate_population — set by RND on menu cycle days. Used for planning: drives
recipe and food quantity scaling and shopping list generation quantities. This
is RND's estimate of how many servings will be needed for that day.

Whenever estimate_population changes, the system must immediately:

Rescale recipe servings.
Recalculate ingredient quantities.
Recalculate shopping list quantities.
Recalculate the procurement's estimated total cost.
Recalculate the procurement's Estimated Budget Per Head Per Day.

served_population — set by FSS on meal prep logs on the actual day of prep,
based on the real diet list or census from the hospital. Used for calculating
actual budget per head per day after the fact. FSS only sets this — RND does
not touch it.

These two fields are fully independent. Changing one never affects the other
in any code path.

Population cascade and last-write-wins rule:
RND can set estimate_population in two places:
  1. Individually per menu cycle day when building the menu plan
  2. At the shopping list level for the whole procurement span at once

Whichever was written most recently wins and cascades. Specifically:

When RND sets population on a shopping list (draft or pre-conversion):
  - Update estimate_population on all menu cycle days within that span
  - Rescale all recipes and food items for those days to the new serving count
  - Recalculate shopping list quantities based on rescaled amounts
  - Record a timestamp so individual day edits after this can override it

When RND sets population on an individual menu cycle day:
  - Update only that day's estimate_population
  - Rescale that day's recipes and food items
  - If a draft shopping list exists covering that day, recalculate its
    quantities for that day only
  - Record a timestamp so a future shopping list population write overrides it

Last write always wins regardless of where the write came from. The timestamp
comparison decides which value is authoritative.

Cross-cycle cascade edge case — flag for agent:
When a shopping list spans two menu cycles (e.g. Fri→Mon where Fri-Sun belong
to Cycle A and Mon belongs to Cycle B), cascading a single population value
from the shopping list will touch days in both cycles. If Cycle B is still a
draft or inactive cycle being edited by RND, this cascade could interfere with
work in progress. Additionally if multiple draft shopping lists overlap on the
same dates there is ambiguity about which list to recalculate when a day's
population changes individually. Agent must identify whether this is a current
flaw in the codebase and propose a solution before implementing the cascade
logic. Flag the proposed solution for review before building.

Once a shopping list is converted to a PO, its line item quantities, vendor
groupings, and structural data are frozen permanently. However the PO enters
an open execution phase for operational details — see Step 3 for the full PO
lifecycle.

RND and FSS can both view the profile of each food and recipe in the menu plan
and must see the current scaled servings based on the active estimate_population
for that day. This view is read-only for FSS.

Menu cycle activation guard:
A menu cycle cannot be set to active unless every day that has at least one
recipe or food item assigned also has an estimate_population value set. If any
such day is missing it, block activation and return a clear error listing which
specific days are missing population. Do not silently allow activation with
blank days.

Shopping list generation guard:
When generating a shopping list, block generation and return a clear error
listing the specific dates with missing population only if a day has zero or
null estimate_population AND has at least one recipe or food item assigned to
it. If a day has no menu items assigned, allow zero population — this supports
manual-only shopping lists for special events or supplies-only runs where no
menu cycle is involved. This guard is defense-in-depth on top of the activation
guard.

--- Food Service End-to-End Flow Clarifications ---

The intended food service flow is:

1. RND creates food service recipes with ingredient breakdowns.
2. RND creates menu cycle days / meal plans from recipes or ready-to-serve FS items.
3. RND sets estimate_population per planned menu cycle day. This is planning-only.
4. Suggested shopping list generation takes a start_date and end_date, resolves each calendar date to the covering menu cycle, then extracts ingredients only from the matched menu cycle day for that exact date.
5. If a date has no covering cycle, no menu cycle day, no menu items, or missing estimate_population where menu items exist, the system must flag/notify the exact date and reason:
   - no covering menu cycle
   - menu cycle day not created yet
   - menu cycle day has no menu items
   - menu cycle day has menu items but no estimate_population
6. Fri-Mon or any procurement span crossing two menu cycles must work. Each date uses its own matched menu cycle.
7. Shopping list converts to one PO with vendor groups.
8. PPA is generated from the PO/procurement event, not directly from a whole menu cycle. It inherits the PO's procurement span, items, estimated cost, vendor grouping, and later final execution values.
