# NCP data meaning

Verified against committed source: `b9a6839f34b5203995d7c61c6f29cd9b0dd03f4f` plus census classification and nullable-recall changes in this working tree (2026-10-28).

Purpose: explain important clinical data families and route maintainers to their authoritative writers/consumers. No patient data or independently certified clinical guidance is included.

| Fields / family | Meaning and authority |
|---|---|
| NcpRecord.patient_id, rnd_user_id, type, status | Cycle context and ownership; [NcpRecord](../../../backend/app/Models/NcpRecord.php), [NcpRecordController](../../../backend/app/Http/Controllers/RND/NcpRecordController.php), [NcpAppointmentWorkflow](../../../backend/app/Services/NcpAppointmentWorkflow.php). Check transitions/permissions, not only a status label |
| risk_score, risk_score_manual_override, risk_score_manual_factors | Calculated score and explicit override metadata; [RiskScoreCalculator](../../../backend/app/Services/RiskScoreCalculator.php), cycle model and assessment/save routes. Score has a decimal:2 model cast; do not turn it into an AI-generated diagnosis |
| Assessment.nutritional_status | Screening-derived classification written by [AssessmentController::saveRiskScore](../../../backend/app/Http/Controllers/RND/AssessmentController.php) using [RiskScoreCalculator](../../../backend/app/Services/RiskScoreCalculator.php), including manual risk-factor overrides. Values include Normal, Moderate Malnutrition and Severe Malnutrition; these labels alone do not establish a clinical malnutrition diagnosis. The intervention calculator does not automatically consume this field as its clinical nutrition status. Confirmed liver calculation status is supplied separately through calculation_options.nutrition_status. Verified against `79ee23b53a0ba047faa791cdb8e5b7fcb1211429` on 2026-10-25; see [intervention source and default boundaries](../../logic/intervention-goals.md#5-adult-goal-calculations-sources-versus-proposed-defaults) |
| bmi_classification, bmi_reference_date | Derived read-only API fields, not stored columns. Assessment::classifyBmi uses the cycle date and completed age months: official WHO 2007 sex-specific bands at 61–228 months, Asia-Pacific afterward; month 60 has BMI without classification. WHO cutoffs are strictly below −3/−2 SD for severe thinness/thinness and above +1/+2 SD for overweight/obesity. Offline expanded-table thresholds retain published 0.001 precision in backend/resources/who-bmi-for-age.json and the matching frontend/lib copy; source URLs, retrieval date and workbook hashes are embedded. No interpolation, exact z-score or runtime fetch. Unknown required age/sex, invalid BMI, edema or maternal status withhold class. Ages 0–4 omit BMI in assessment/monitoring writes, API, AI and new reports; older stored values are preserved. Adult IBW/BMR/TEE panel estimates and monitoring IBW targets are withheld through month 228; the prescription engine retains its existing methods. AssessmentResource exposes the reference date and strips neither raw height nor weight; the web strips derived fields from saves. NcpSummaryGenerator prints classification separately from risk; census uses separate pediatric and adult classification buckets. Monitoring AI uses observed_at. PES anthropometric eligibility treats the WHO age range as pediatric, preventing adult BMI/GLIM rules from establishing a pediatric diagnosis |
| Assessment.weight, height, dry_weight_kg, edema_present | Measurement/context inputs; [Assessment](../../../backend/app/Models/Assessment.php), [InterventionCalculationContextService](../../../backend/app/Services/InterventionCalculationContextService.php) maps weightKg/heightCm and chooses the measured/dry weight basis. Trace field_sources/measurement date rather than assuming the assessment is always the newest source |
| muac_mm, waist_cm, hip_cm | Different explicit units in Assessment. Preserve request limits and conversions; do not apply one shared unit by appearance |
| MUAC screening display | [getMuacScreening](../../../frontend/lib/anthropometricSafety.ts) uses known age at the classification reference date and mm: only 6–59 months receive Very low MUAC (<115), Low MUAC (115–<125), or Above screening cutoff (>=125). These are screening observations, not automatic MAM/SAM or adult malnutrition diagnoses. Measurements remain visible for other/unknown ages without a derived label. Above-cutoff values are omitted from the generated RND summary. Pediatric WHO growth z-scores are not automatically calculated |
| food_recall, intake_nutrients, allergies, food_dislikes | Structured clinical inputs in Assessment; [FoodRecallService](../../../backend/app/Services/FoodRecallService.php), [RecommendService](../../../backend/app/Services/RecommendService.php) and [MealPlanService](../../../backend/app/Services/MealPlanService.php) consume relevant food/intake context. Explicit food_recall=null is valid for an unused or cleared recall; a populated recall still requires displayed_micros, days and valid item quantities/units. Read the selected calculation path before changing the JSON shape |
| Recipe.category | Menu Items use `meal`, `carb`, `snack`, or `tube_feeding`; StoreRecipeRequest validates creation/edits. RecipeController search defaults to Oral categories; explicit `nutrition_support=tube_feeding` selects formulas and `library` permits management of all categories. Oral menu and template writers reject tube categories. Food Calculator uses Food Recall without patient-record persistence |
| NcpRecord.nutrition_support; Intervention.nutrition_support | Single `oral`, `tube_feeding`, or `no_food_menu` choice. AssessmentController writes the cycle choice; missing choices block assessment completion and new intervention saves. A forward data migration fills existing missing choices with Oral. InterventionPlanService captures the cycle choice on creation and protects saved plans from later cycle-mode changes. PatientMenuPlanGenerator and NcpSummaryGenerator consume saved intervention mode; no-food reports need no weekly menu |
| Intervention.formula_items; MealPlanTemplate.formula_items | Ordered JSON collection, not calendar days or daily intake. FormulaPlanService derives trusted snapshots from existing Recipe calculation, owned source templates/interventions or a validated transient Menu Item. Plan-only creation writes no Recipe/FoodItem. Source UUIDs are checked server-side; snapshots persist independently. Templates can capture a saved intervention; library template profiles only select/remove items |
| Formula portion_multiplier, nutrient_snapshot, original_snapshot | Multiplier applies to the whole recipe; a new library formula starts at 1x. Snapshot nutrients are per serving and ingredient quantities are whole-recipe amounts; displayed totals multiply nutrients by recipe_yield and multiplier. Ingredient edits become the current local baseline, so changing 2x to 3x multiplies displayed current amounts by 1.5. Reset restores original_snapshot at 1x. FormulaCollection and formulaItemsPayload send measured ingredients; FormulaPlanService recomputes nutrients and ignores client totals. Saved displayed_nutrients preserves selected micros even without numeric limits; populated legacy prescription limits also remain visible. Formula selectors show individual macros/micros without summing the collection. Name-only cards reuse MenuEditorSlots; profiles and Tube PDFs show exact planned ingredients. Selected formula totals include fluid via the existing foodFluidBalance estimate from captured water_g; it is not a new daily sum or prescription-scaling target. Oral fluid totals/details share the macro tracker. Multipliers remain editor metadata. PDFs put portion details before macros and every selected micro, marking unavailable data Not recorded rather than zero |
| Oral nutrient_snapshot.recipe_reset_baseline / recipe_reset_quantity | MealPlanItemController captures the original saved recipe and quantity on first edit. MealPlanSection preserves ingredient edits and additions while uniformly changing servings; Reset restores captured amounts. Copying a template/previous menu starts a fresh reset baseline. Food Library and source templates are independent. Missing yields or incompatible measured ingredient units require correction; no invented 1-serving baseline |
| Assessment.dietary_intake | Optional Food recall notes, edited beside the recall calculator using the existing 250-character field and Assessment request/save path. [PesEvidenceBuilder](../../../backend/app/Services/Diagnosis/PesEvidenceBuilder.php) includes this narrative as assessment evidence; editing it can reopen relevant diagnosis reviews |
| Diagnosis review intake evidence | `FoodRecallService::evidenceSummary` derives sample-day averages from frozen nutrient snapshots and compatible saved portions; `intakeEvidence` supplies explicit units for separately entered amounts. Macro values retain kcal/g units and supported micronutrients use the existing monitoring unit definitions. No density assumption, unknown-to-zero substitution or addition of entered and calculated estimates. Food identifiers/names are excluded from provider summaries; see [AI maintenance](ai.md) |
| PesSuggestionState.provider_metadata | [PesSuggestionService](../../../backend/app/Services/Diagnosis/PesSuggestionService.php) writes per-candidate hashes, relevant keys and explicit review outcomes. Status/generation/resolution reuse them. Complete/valid empty results close their candidates. Rejected or partially accepted output permits deliberate retry, never an automatic refill. Legacy deletion resolves current problem components or the matching domain's Other candidate. Relevant required/corroborating/cited evidence changes reopen review; related deletion removes retained drafts and matching review contexts. See [AI maintenance](ai.md) |
| Referral/medication AI context | Patient.medical_diagnosis is referral information; Assessment.primary_diagnosis_category/other groups nutrition care and is not medical diagnosis. Assessment.medications contains clinician-entered text. [ClinicalAiContext](../../../backend/app/Support/ClinicalAiContext.php) allowlists and redacts these fields for diagnosis evidence and monitoring comparisons; provider guidance never becomes patient evidence |
| Diagnosis justification notes | [PesSuggestionService](../../../backend/app/Services/Diagnosis/PesSuggestionService.php) maps provider n/en/sn into extra_notes and builder_data.etiology_notes/sign_notes using [DiagnosisBuilder](../../../backend/app/Support/DiagnosisBuilder.php). Accept/edit/save preserve notes separately from core PES. Generated notes allow 100 characters; manual notes 125. Provider instructions request an assessment fact and why it supports each part. Unsupported, missing, repeated or component-only optional wording becomes empty; no fallback repetition or extra call. Existing UI omits empty notes. Core P/E/S validation remains mandatory; see [AI guard limits](ai.md) |
| Diagnosis.builder_data.ni_nutrient | The existing diagnosis page writes the selected nutrient string, at most 50 characters, and DiagnosisBuilder composes the Intake problem from direction + nutrient + Intake. Vitamins and Minerals now use native dropdowns with 13 vitamin and 15 mineral choices; names were checked against [NIH ODS nutrient information](https://ods.od.nih.gov/factsheets/list-VitaminsMinerals/). These are name choices, not dose/deficiency criteria. Editing recognized values restores the group. Historical unlisted vitamin wording remains a selected legacy option; unrelated custom substances retain their existing custom editor. No stored diagnosis is renamed. AI edit/approval and reports continue to consume the same string/PES contract |
| Intervention.energy_kcal, protein_g, carbs_g, fat_g, fluid_ml | Saved prescription quantities with decimal:2 casts; [Intervention](../../../backend/app/Models/Intervention.php), [NutritionPrescriptionService](../../../backend/app/Services/NutritionPrescriptionService.php), [InterventionPlanService](../../../backend/app/Services/InterventionPlanService.php). Generated reports round macros to whole numbers; other clinical numeric report displays trim unnecessary zeros. Stored precision and other website nutrient displays remain unchanged |
| goal_type, disease_stage, calculation_options, calculation_snapshot | Goal and calculation context/history; follow the plan service and [calculation context](../../../backend/app/Services/InterventionCalculationContextService.php). The snapshot is not a fresh recomputation against today's measurements. [PatientMenuPlanGenerator](../../../backend/app/Services/Reports/Generators/PatientMenuPlanGenerator.php) formats the saved Mifflin, clinical kcal/kg, or pediatric EER terms with maternal energy and any deficit/surplus for the Nutrition Intervention Plan PDF; manual plans without a calculated energy do not show an equation. It does not recalculate the prescription |
| source_monitoring_id and latestIntervention | Links follow-up input to intervention history; NcpRecord selects latest intervention by created_at/id, while Intervention's update hook protects historical plans. Preserve those meanings across API/report changes |
| Monitoring indicators/comparisons | [MonitoringPlanService](../../../backend/app/Services/MonitoringPlanService.php), [MonitoringSummaryService](../../../backend/app/Services/MonitoringSummaryService.php), [Monitoring](../../../backend/app/Models/Monitoring.php). Baselines, targets and comparisons are different values; AI narrates bounded evidence. Only the newest saved entry by internal ID is editable/deletable in draft/active cycles, enforced in MonitoringController and exposed as can_edit/can_delete. Recall edits preserve saved nutrient baselines. clinical_summary is required with a 700-character limit. Reports print the saved evaluation and numeric intake; intake notes and symptoms feed AI instead of separate report columns |
| Monitoring AI recall_targets | Transient provider context written by `MonitoringPlanService::draftComparison`, consumed by `AIService::narrateMonitoring`. Maps only populated recall nutrient keys to existing prescription unit, target and reference bounds from plan indicators. Uses kcal/g/mg/other indicator units without conversion; unknown guides are omitted. Does not merge recall estimates into entered `indicators.current` readings or persist a new prescription. See [AI maintenance](ai.md) |
| Census classification basis and history | DemographicCensusGenerator basis 9 classifies each qualifying ADIME cycle's initial Assessment with Assessment::classifyBmi, using age in completed months, sex, edema and maternal context at cycle start. Monitoring and screening-derived nutritional_status are not classification sources. `by_bmi_classification` separates ordered pediatric (Severe thinness, Thinness, Normal, Overweight, Obesity) and adult (Underweight, Normal, Overweight, Obese Class I, Obese Class II) buckets, including zeros. Unsupported or missing context stays Unspecified in the compatibility `by_status`/API `by_nutritional_status` counts. Nutrition care categories reuse PrimaryDiagnosisCategory order and include zero counts. ReportController serves current-basis frozen snapshots unchanged; older-basis periods recalculate on read and are labeled live, without updating stored census rows. Month/year and PDF share this summary. Nutrition support retains its unrecorded bucket internally but the screen/PDF display only the three named modes |
| FoodItem.serving_size, serving_unit, micronutrients, water_g | Clinical food quantities and structured nutrient data; [FoodItem](../../../backend/app/Models/FoodItem.php), [UsdaService](../../../backend/app/Services/UsdaService.php). USDA nutrient keys/mapping must stay compatible with recipes and clinical rules |

Use [NCP maintenance](README.md) for HTTP owners, tests and domain explanations, and [general data tracing](../platform/data-semantics.md) before editing. Clinical recipes/FoodItem and operational FoodServiceRecipe/FsItem are distinct models; do not merge their units or calculations by field-name similarity.

Before changing clinical data, establish the relevant record shapes, migration history and clinical requirements. This selected map does not enumerate every clinical field; locate additional fields through models/requests and document only the behavior inspected.
