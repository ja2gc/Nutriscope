# Shared features and role-specific consumers

Purpose: locate features used across roles and distinguish their shared backend rules from role-specific presentation. Shared does not mean every role can perform every action.

`RecoveryEmailController::cancelPending` owns cancellation of an unfinished recovery-email change: authenticated active users can clear their own pending address/code while preserving the verified recovery address and onboarding flags. Initial unverified addresses are cleared. Verification and cancellation take the same user row lock, and cancelled codes cannot be accepted. Explicit `destroy` remains the operation that removes the current recovery address. The web Profile shell owns the display/actions/email/code steps; native consumers keep their existing flow. See the [API overview](../../operations/api-overview.md#authentication-and-account-access).

## Meaning and safe changes

Announcement audiences (source review: `1ba3d15f` plus the audience change, 2026-11-05): `StoreAnnouncementRequest` / `UpdateAnnouncementRequest` write `audiences`, a nonempty, unique list of RND, FSS and/or Admin roles. Null means a legacy post: `Announcement::audienceRoles()` falls back to `visibility` (All means all three). A legacy visibility-only update clears the explicit audience list; a text-only update preserves it. The author is not automatically a recipient. The shared controller filters role feeds and protected images; authors retain access to their posts and Admin retains oversight access. `NotificationService::fanOutAnnouncement` targets active users in the selected roles, excluding the author. Editing audiences changes current access without sending another notification or retracting previously delivered notifications.

`AnnouncementAudienceSelect` is reused by the web board and RND dashboard composers. Audience labels appear only in create/edit controls. Board, dashboard and native announcement cards/details show category and pinned state as plain neutral text. The nullable audience column is added by `2026_11_05_000001_add_audiences_to_announcements_table`; existing posts are not backfilled. See [data tracing](../platform/data-semantics.md) before changing audience semantics.

Help content stays in the existing web/mobile content arrays. Questions focus on task prerequisites, recovery and troubleshooting; navigation catalogs, other roles' permissions and server internals belong in the manuals. Web filters still show Shared plus the signed-in role; native Help shows Shared/FSS. Sign-in copy calls FSS users **kitchen staff**; the stored role and Android package remain unchanged.

`AnnouncementResource` accepts the index query `attachment_format=urls` to return protected application paths in the existing `attachment`/`attachments` fields. Omitted format or `inline` retains the older data-URL response for installed clients. `AnnouncementController::attachmentFile` checks role visibility and association with the selected announcement before serving bytes; storage keys never enter the response. Older inline records use a position within that announcement's attachment array and remain unchanged in storage. These paths are representations of current attachments, not permanent attachment identities.

Web boards/dashboard request compact feeds, then request the original inline representation when an image-bearing editor opens. Text-only saves omit unchanged attachment fields; changed image collections still use the existing full replacement validation/storage contract. Native feeds request compact output and `AnnouncementMedia` sends bearer authentication for protected images. Both inline and compact representations remain supported; no offline cache, new write contract or database migration is introduced. Trace these consumers before changing attachment fields.

User role/is_active and onboarding/recovery flags in User affect access and setup; don't interpret a hidden control as authorization. Check route middleware, request authorization and ownership, then both clients. A controller under RND/ can still serve shared routes.

Notification read state, dismissal, source linkage and retention are distinct from the source business event. Trace NotificationLifecycleService and scheduled pruning before changing their meaning. Don't make announcements/SOP changes for only one recipient role.

Dashboards combine different domain data. A shared layout is not evidence that counts, permissions, filters or time windows should be identical. Report data may use historical snapshots; don't replace it with live catalog values without tracing its generator.
