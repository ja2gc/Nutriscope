# Web

Purpose: find Next.js screens, existing controls and API transport.

`app/(rnd)/layout.tsx` gives narrow RND screens a white background; desktop retains the existing warm page background. Shopping-list detail and its copy summary remove outer card padding on narrow screens while retaining cards at the large breakpoint. The purchase table keeps its own horizontal scroller. Its column header uses `warm-100` with darker `warm-700` text; package/other-item separators use the lighter `warm-50`, against white item rows.

Page section tabs remain a single horizontal row at narrow widths: bounded containers scroll horizontally and buttons do not shrink or wrap their labels. `components/ui/Tabs.tsx` owns the shared compact 44-pixel-minimum layout for Food Library, Inventory, Reports and admin screens; its optional fill behavior applies from the small breakpoint upward. `TabBar` follows the same scrolling boundary. Procurement, patient profiles, assessment referral sections, diagnosis domains, Announcements/SOP and accomplishment views keep their existing state/leave handlers with the same containment. `NcpSectionTabs` already uses this pattern.

Non-profile uploads share `FileUploadField` for drag-and-drop, keyboard/click selection, visible limits and feedback. Actions stack below the heading on narrow screens. `ImageUploadGallery` provides image-only thumbnails with an individual X; `RemoveButton` is shared with Menu Calendar/template actions. `ImageViewer` provides plain image viewing, arrows, exit and permitted removal, with keyboard focus management. Filenames are not shown as captions.

Announcement images save with Post/Save; procurement images save immediately and precede Mark vendor received. `ImageFilePicker` supports one logo per slot; clearing a replacement restores the saved preview. `ReportsBrowser` submits selected files, including drops. Assessment retains single-file PDF/image uploads and document rows. Existing validation, permissions and storage contracts remain authoritative.

The `ImageUploadGallery` avatar variant uses the circular preview and camera badge as a keyboard-accessible popover trigger for choosing/changing or removing the image; `avatarFallback` supplies the user's initial. `ProfilePageShell` keeps that picker beside the name, initializes its preview from the saved photo, stages replacement/removal through the existing `profilePhotoUpdate` intent and restores the saved preview on cancel. Applying a crop opens the account editor; changes are not saved until **Save Changes**.

Admin and RND Profile routes share `ProfilePageShell`: one continuous white card leads with the photo, name and role, followed by account details and divided recovery/password rows. Each section action stays in the right grid column at all widths; short visible labels retain full accessible names. Recovery displays the current address, with Edit opening Change/Remove/Cancel actions. Replacement email and verification-code forms are separate steps; only a successful code-send response opens the code form. Cancel calls the pending-only cancellation endpoint before returning to the current address. Verification guidance uses `InfoHint` beside the heading, with optional trigger sizing classes for the touch target. Success feedback clears after three seconds; errors remain until addressed. `AuthContext.refreshUser` adds a per-refresh revision query to protected profile-photo URLs so existing header/profile images reload after replacement; binary authorization is unchanged. Page introductions are omitted; identifiers, status, field instructions and help content remain separate from introductory copy. Help category headers use `warm-100` with `warm-200` dividers above white question rows.

Patient-directory search cancellation: each debounced search/filter/page effect owns an AbortController. Cleanup cancels pending debounce and in-flight fetch; aborted responses and errors cannot update the list or loading state. `patientService.fetchPatients` accepts an optional final AbortSignal; existing callers retain their defaults. This is transient request cancellation, not patient-data caching.

Low-bandwidth loading changes: Diagnosis fetches AI status independently of required clinical data and keeps generation disabled while that status refreshes. Monitoring history pagination fetches only history; mutations still reconcile the care context. Patient profiles load past cycles independently of patient/current-cycle readiness. Assessment lookups preserve HTTP status so a real 404 can be distinguished from a failed connection before enabling editing. Required-read errors offer retry. No clinical calculation or completion rule changes.

Intervention's `loadPlans` reuses the full latest-plan response when the selected public UUID matches it, avoiding a second serial detail read. Explicit older-plan links still load that plan and retain read-only history behavior. The `latest` and `showPlan` actions both return `InterventionResource`; this is local response reuse, not a cross-page clinical cache.

NCP navigation and planner loading: the sidebar explicitly fully prefetches the four steps only for a real selected cycle; available profile step links also fully prefetch. Next.js handles route/code reuse in production; these links do not mount clinical pages or cache their API responses. Intervention mounts Food / Nutrient Delivery on first opening, dynamically loads `MealPlanSection` with the existing loading indicator, and keeps the editor mounted thereafter to preserve drafts across tabs and saves. Opening Plans alone no longer starts meal-planner reads. No persistent clinical cache or workflow change is introduced.

Procurement list and PO pagination have separate loaders. Procurement directories and Inventory browsing no longer enumerate supplier pages; complete choices load when an editor/detail needs them, with retry before editing. Announcements use the [compact delivery contract](../shared/README.md#meaning-and-safe-changes). These changes introduce no persistent cache or offline saves. Local production-build throttling is recorded in the ignored implementation plan; it is not a deployed performance guarantee.

Procurement tables reuse the shopping-list layout: a bounded, keyboard-focusable region scrolls horizontally around a table with a minimum width. Item, list, PO and vendor names stay on one line; headers also stay on one line. The Procurement page owns list, PO and receiving tables; `SuppliersPanel` owns the supplier directory. Directory pagination stays outside the horizontal scroller. Shared `Pagination` wraps its summary and controls when needed and provides 44-pixel button targets. Contact summaries retain their existing layout.

Website loading feedback: `SectionLoading` accepts optional `skeleton` presentation for existing initial/section loading branches, including the RND route fallback, Intervention, food-service lists/details, Budget and report browsing. The default remains an inline indicator for small tasks. Skeletons contain only decorative warm-gray rows, named loading status and reduced-motion-safe animation; they have no controls, fake values or minimum duration. Existing custom Dashboard, NCP, Food Library, announcement and SOP placeholders retain their layouts with named status and reduced-motion support. Shared Budget/report/notification/announcement owners keep the same behavior for their other role consumers. Page-local loading flags and quiet mutation refreshes remain authoritative; skeletons do not add requests or replace loaded forms during an existing quiet refresh.

Remaining main-page feedback: the admin route fallback, Users, Audit Logs/history and Backups reuse `SectionLoading`. Admin Dashboard and its AI usage chart keep their existing placeholder layouts with named busy status and reduced-motion-safe animation. Admin and RND Settings show the shared skeleton only for the server-loaded budget setting; local preferences remain available. Static Help/Profile content and authentication guards are unchanged. Loading feedback does not alter authorization, audit retention, backup operations or request sequencing.

The open mobile drawer contains keyboard focus. Both roles label their home destination **Dashboard**.
