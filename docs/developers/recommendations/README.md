# Developer recommendations

Proposed improvements for future developers. Start with the [grouped developer index](../README.md) and [current architecture](../platform/architecture.md) for implemented behavior. These recommendations do not authorize migrations, deployment, or production changes.

## Connectivity: current behavior and future work

Connectivity inspection verified against source: `db7bff65dd597e2cab4ddcd83ded569ff88dd03a` (2026-10-29). The proposals below are future work, not implemented capabilities or an approved implementation specification.

### Current boundaries

- Web and mobile workflow saves call the Laravel API. The inspected clients do not provide a general durable offline outbox, automatic replay, or a shared version-conflict protocol. A failed request must not be presented as a confirmed server save.
- Web [login](../../../frontend/app/api/auth/login/route.ts) stores the bearer token in an HttpOnly cookie with a seven-day lifetime. [AuthContext](../../../frontend/contexts/AuthContext.tsx) fetches the current user on startup and clears its user state when that fetch fails. [The current-user proxy](../../../frontend/app/api/auth/me/route.ts) also treats any non-success upstream response as unauthenticated. Connectivity failures and authentication failures need distinct handling before supporting offline startup.
- Mobile [auth](../../../mobile/lib/auth.ts) persists the token in SecureStore. [The root layout](../../../mobile/app/_layout.tsx) creates an in-memory React Query client; this does not persist workflow records or pending mutations across process restarts. AsyncStorage is installed and used for [preferences](../../../mobile/lib/prefs.ts), not a general workflow outbox.
- [Mobile login](../../../mobile/app/login.tsx) supplies the shared device name `Expo App`; web login omits a device name. [AuthController](../../../backend/app/Http/Controllers/Auth/AuthController.php) revokes the user's existing tokens with the supplied name, or the default name, before issuing a replacement. Distinct per-installation identities are a prerequisite for supporting independent concurrent sessions of the same client type.
- [LegacyAppCleanup](../../../frontend/components/mobile-app/LegacyAppCleanup.tsx) removes the old `/fss/` service-worker registrations and `nutriscope-fss-` caches. The inspected web sources contain no replacement general offline service worker. The current role boundaries remain RND/Admin on web and FSS on native mobile.

### Small improvements for slow connections

Keep this work separate from offline synchronization. Existing API authorization, validation and successful-response requirements still apply.

1. First candidate: explicitly disable automatic route prefetch on [Sidebar](../../../frontend/components/layout/Sidebar.tsx) and [MobileBottomNav](../../../frontend/components/layout/MobileBottomNav.tsx) links. These currently use Next Link's default prefetch behavior. This limits speculative route downloads, with the tradeoff that opening a destination may require downloading its resources then. It does not reduce that destination's own API payloads or implement native-app caching. Verify the actual benefit in a production build; automatic prefetch is disabled in development.
2. Profile repeated requests and payload sizes before adding caching. Reuse the [existing refresh convention](../platform/web.md) that preserves mounted content during post-save reconciliation. For mobile, inspect each query's freshness needs and mutation invalidation before changing its policy; do not apply a blanket freshness window to clinical or operational data.
3. Check compression in the actual serving topology before changing proxy configuration. Installed Next.js 16.3.3 documents gzip as enabled by default for its server; repository snippets do not establish the live host's compression behavior. Fonts are already bundled through `next/font/local` in [the root layout](../../../frontend/app/layout.tsx).

Do not automatically retry mutations merely because a connection timed out: the server may already have committed them. Measure initial load, navigation, transferred bytes and concurrent requests under throttling, and exercise both RND and Admin navigation. A smaller request budget is not proof of a measured latency improvement.

### Future scoped offline support

The recommended starting point is one client and one bounded workflow, such as FSS daily accomplishment entry. Alternatives are form-draft recovery only, or a much larger conversion of all workflows to offline operation. Draft recovery is smaller but does not guarantee reopening a workflow offline. Whole-system support introduces related-record creation, temporary identity mapping, attachment transfer, workflow ordering and calculation dependencies.

For the scoped approach:

1. **Prepare while online.** Require initial online sign-in and an explicit completed download of the supported workflow's data. Web also needs a cached application shell through a service worker; the native interface is already installed. Only downloaded records and supported screens can be used offline. Account switching and software updates must not expose another user's data or discard pending work.
2. **Persist locally before acknowledging.** Store drafts and pending operations durably, scoped to the signed-in account. Use IndexedDB for structured web data; evaluate the installed AsyncStorage for a small serialized mobile draft store, or SQLite when transactional records and an outbox are needed. Check storage failures. Show distinct states for saved on device, pending sync, synced and needs review. Other clients see changes only after server acceptance.
3. **Replay through existing owners.** Give each operation a stable unique ID, public record identity, base server version, payload and local capture time. Preserve dependent operation order and later edits. Retry transient failures with backoff on app open/resume/reconnect and provide manual retry. Coordinate multiple browser tabs so they do not independently drain the same outbox. Background execution is an enhancement, not a delivery guarantee.
4. **Make server acceptance atomic.** Authorize the authenticated actor and enforce current validation and workflow state through existing controllers/services. Persist the operation's deduplication result with its database effects and return the prior result on replay. Guard generated reports, notifications, audit events and other side effects against duplicate delivery. File effects need their existing compensation paths. Record server receipt separately from untrusted local capture time; never backdate audit events to pretend the server processed work offline.
5. **Detect conflicts.** Compare a server-controlled version atomically before applying a stale edit. All writers, including ordinary online writes, must participate. Preserve both the pending draft and current server record for review when versions differ; do not silently overwrite. Device clocks and last arrival are not reliable clinical or procurement conflict policies. Last write wins may suit independent display preferences. New related records and deletion conflicts need an explicit policy before extending scope.
6. **Retain server authority.** A local save is provisional. [Daily accomplishments](../../../backend/app/Http/Controllers/FSS/DietListCountController.php) reject edits after the period is submitted/approved and prepare report archives after accepted writes. [Served-population updates](../../../backend/app/Http/Controllers/FSS/MealPrepLogController.php) can be locked by completed procurement. A later sync must respect these rules and retain rejected drafts for review. Keep AI requests, report generation, approval/completion and inventory effects online initially; do not duplicate the clinical or procurement engines on clients. See [NCP data](../ncp/data.md) and [food-service data](../food-service/data.md) for existing semantics.
7. **Separate local access from server login.** Keep web tokens in HttpOnly cookies and mobile tokens in SecureStore; never cache passwords or move tokens into localStorage. Cached identity permits only the deliberately scoped local workspace. Define an offline-access duration and device-unlock policy; account revocation cannot be discovered while disconnected. Expired/revoked authentication pauses replay without deleting drafts, and resumption requires the same authorized account.
8. **Minimize sensitive copies.** Define trusted-device enrollment, local encryption/key handling, retention, logout and pending-work recovery before caching patient data. IndexedDB and AsyncStorage alone do not establish a secure local vault. Browser persistence requests reduce eviction risk but are not backups and do not prevent user deletion. Never clear unsynchronized work silently during logout, cleanup or upgrades.

Before implementation, settle the exact workflow/platform, download scope, local retention and offline-access duration, device identity, version field ownership, conflict UI, outbox schema and upgrade behavior. No universal values are selected here. Update the affected domain data guide with the meaning, writer and consumers of any introduced versions, statuses or timestamps; use [data semantics](../platform/data-semantics.md) to trace those changes.

Acceptance must cover offline cold start after preparation, process restart with pending work, storage exhaustion, server commit with a lost response, duplicate replay, edits from two devices/tabs, expired authentication, account switching, a record deleted or locked before sync, and client upgrades with outstanding operations. Use fictional data and the [testing isolation rules](../platform/testing.md).
